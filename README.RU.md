Скилл для Claude Code: превращает обычную просьбу вроде "заведи таск: менеджерам нужен фильтр рейтинга по неделе и месяцу" в аккуратно оформленные задачи GitLab. Проверяет существующие задачи и лейблы, читает код, пишет черновики в `docs/tasks/` на ревью и отправляет их в GitLab только после явного "ок".

## Пример

> **Ты:** заведи таск: в рейтинге рекрутеров только цифры за всё время, менеджерам нужен фильтр по неделе и месяцу

Claude находит лейблы и связанную задачу #85, читает `server/routes/leaderboard.js` и `web/src/pages/Leaderboard.jsx` и пишет два связанных черновика. Вот бэкендовый, его написал скилл на демо-проекте из [`evals/fixtures`](evals/fixtures):

```markdown
---
title: Рейтинг рекрутеров: фильтр по неделе и месяцу (бэкенд)
labels: Backend, Feature ✨, To Do 📋
---
## Описание
Рейтинг рекрутеров показывает только итоги за всё время, поэтому менеджер не видит, кто лучше всех отработал на этой неделе или в этом месяце. Свежие результаты теряются на фоне многолетней истории, и рейтинг нельзя использовать на еженедельных и ежемесячных разборах.

## Цель
Дать менеджерам сравнивать рекрутеров за недавний период, чтобы рейтинг отражал текущую работу и подходил для регулярных разборов команды.

## План реализации
**Технические детали:** `GET /api/leaderboard` в `server/routes/leaderboard.js` считает закрытые вакансии по рекрутерам без условия по дате. Запросу нужен необязательный период, который ограничивает вакансии датой закрытия. Связано: #85 (выгрузка рейтинга в CSV) - когда обе задачи будут готовы, выгрузка должна учитывать тот же период.

*Что нужно изменить:*
- [ ] Согласовать с владельцем продукта: "неделя" - это календарная неделя с понедельника или последние 7 дней, и то же для "месяца"?
- [ ] Принимать необязательный параметр `period`: `week`, `month` или `all` (по умолчанию `all`, чтобы текущие клиенты работали как раньше).
- [ ] Для `week` и `month` фильтровать вакансии по дате закрытия; проверить, что `vacancies` хранит эту дату, и добавить колонку миграцией, если нет.
- [ ] Отвечать 422 на неизвестное значение `period`.

## Критерии приёмки
*Как понять, что задача готова:*
1. `GET /api/leaderboard` без параметров возвращает те же цифры за всё время, что и раньше.
2. `GET /api/leaderboard?period=week` и `?period=month` учитывают только вакансии, закрытые в этом периоде.
3. `GET /api/leaderboard?period=year` возвращает 422.
```

> **Ты:** ок, закинь в гитлаб

```
#91  Рейтинг рекрутеров: фильтр по неделе и месяцу (бэкенд)  https://gitlab.example.com/demo/app/-/issues/91
#92  Рейтинг рекрутеров: фильтр по неделе и месяцу (фронт)   https://gitlab.example.com/demo/app/-/issues/92  linked #91
```

Во фронтовой задаче теперь написано `Зависит от задачи "Рейтинг рекрутеров: фильтр по неделе и месяцу (бэкенд)" (#91)`.

## Что умеет

- Проверяет существующие задачи на дубли: при полном совпадении спрашивает "переоткрыть #N или заводить новую", смежные упоминает как "Связано: #N".
- Берёт только существующие лейблы проекта и копирует стиль свежих задач. Неизвестный лейбл не даст отправить задачу, иначе GitLab молча создал бы новый.
- Пишет задачу на языке запроса (русский или английский) и для двух аудиторий: "Описание" и "Цель" простым языком для QA и менеджеров, "План реализации" с техническими деталями из кода для разработчика.
- Делит работу на бэкенд и фронт и связывает задачи: номер бэкенд-задачи подставляется в описание фронтовой, плюс связь `relates_to` в GitLab.
- Баги, найденные попутно, не прячет в задачу, а предлагает завести отдельно.
- Переносит ранее сделанную работу с её историей: по просьбе ставит `created_at` в прошлом, в рабочие дни и часы, не в будущем и не раньше задач, на которые есть ссылки.
- Не создаёт задачу дважды: после отправки номер задачи (`iid`) записывается в черновик.

## Установка

Как плагин Claude Code (рекомендуется, обновляется через `/plugin`):

```
/plugin marketplace add mattsyntax/gitlab-task-skill
/plugin install gitlab-task@gitlab-task-skill
```

Или как обычный скилл:

```bash
git clone https://github.com/mattsyntax/gitlab-task-skill.git ~/.claude/skills/gitlab-task
```

Нужны `python3` 3.9+ (только стандартная библиотека) и `git`. После установки перезапусти Claude Code.

## Настройка проекта

В корневом `.env` репозитория, где заводятся задачи (файл должен быть в `.gitignore`):

```
GITLAB_ACCESS_TOKEN_WRITE=<personal access token со scope api>
# только если API не на https://<хост из origin>/api/v4:
GITLAB_API=https://gitlab.example.internal/api/v4
```

- Проект определяется по `git remote get-url origin`. Переопределить можно через `GITLAB_PROJECT=group/repo`.
- Вместо `GITLAB_ACCESS_TOKEN_WRITE` подойдёт `GITLAB_TOKEN`. Переменные окружения важнее `.env`.
- Дата создания (`created_at`) применяется, только если токен принадлежит админу или владельцу проекта. Иначе GitLab ставит текущую дату.
- Шаблон задачи берётся из `docs/tasks/00-index.md` проекта. Если его нет, скилл создаст его из `assets/task-template.ru.md` или `assets/task-template.en.md`, в зависимости от языка запроса.

### Попробовать без токена

Укажи в `GITLAB_MOCK` папку с `labels.json` и `issues.json` (формат см. в [`evals/fixtures/gitlab`](evals/fixtures/gitlab)). Тогда скрипт отвечает из этих файлов, не ходит в сеть, а `create` только печатает, что отправил бы:

```
GITLAB_MOCK=.gitlab-mock
```

## Как пользоваться

Просто попроси в Claude Code по-русски или по-английски, своими словами. Примеры:

- `создай задачу: эндпоинты списков для выбора привести к kebab-case`
- `заведи таск: в рейтинге нужен фильтр по неделе и месяцу`
- `заведи баг: при загрузке фото сотрудника падает 404`
- `закинь в гитлаб` - после ревью черновиков
- `create an issue: add a period filter to the leaderboard`

Поддерживаются русский и английский: и фразы запуска ("создай задачу", "заведи таск", "create an issue", "file a bug"), и подтверждения ("ок", "закинь в гитлаб", "go ahead", "push it to gitlab"). Задача заводится на том языке, на котором ты попросил: по-русски с разделами Описание / Цель / План реализации / Критерии приёмки, по-английски с Description / Goal / Implementation plan / Acceptance criteria. Лейблы остаются как в проекте.

Порядок всегда один: исследование (лейблы, дубли, код), черновики в `docs/tasks/`, ревью и проверка через `--dry-run`, твоё "ок", отправка, список ссылок.

## Скрипт

`scripts/gitlab.py` можно запускать и вручную из папки репозитория:

| Команда | Что делает |
|---|---|
| `labels` | список лейблов проекта |
| `issues [--state all\|opened\|closed] [--out file.json]` | все задачи, постранично по 100 |
| `issue <iid>` | одна задача с описанием |
| `create <file.md> [--dry-run]` | отправить один черновик |
| `create-all [dir] [--dry-run]` | отправить все черновики без `iid`: зависимости первыми, остальные по дате |
| `dates --from YYYY-MM-DD [--to YYYY-MM-DD] --count N [--tz +03:00] [--seed N]` | подобрать даты в рабочие дни и часы |
| `relabel "Старый" "Новый" [--dry-run]` | заменить лейбл на всех задачах |

## Формат черновика

```markdown
---
title: Короткий понятный заголовок
labels: BUG 🐛, Backend, To Do 📋, 🔴 High priority
created_at: 2026-09-23T14:26:00+03:00   # необязательно, при переносе ранее сделанной работы
depends_on: 11-manual-bonuses.md        # необязательно, для фронтовой половины
---
## Описание
## Цель
## План реализации
**Технические детали:** ...
- [ ] ...
## Критерии приёмки
1. ...
```

После отправки скрипт дописывает в шапку `iid: <номер>`, и повторный запуск такой файл пропускает.

## Безопасность

- Токен читается из окружения или `.env` и никогда не выводится. Скилл запрещает Claude выводить `.env` или делать по нему `cat`.
- Адреса API с `http://` отклоняются, потому что токен ушёл бы открытым текстом. Если внутренний GitLab умеет только HTTP, включи это сам: `GITLAB_ALLOW_INSECURE=1` в `.env`. Скилл этого никогда не предлагает.
- Без твоего явного подтверждения ничего не отправляется, а перед каждой отправкой проходит проверка `--dry-run`.

## Разработка

```bash
bash tests/smoke.sh                          # офлайн-тест всех команд скрипта в мок-режиме
claude plugin validate --strict .            # манифесты
claude plugin eval . --scaffold --allow-tools Bash Write Edit --trust-plugin   # поведенческие evals, платные вызовы модели
```

Первые две команды CI запускает на каждый push. Evals из [`evals/`](evals) разворачивают демо-репозиторий с мок-данными GitLab и проверяют, что скилл делит работу на бэкенд и фронт, ловит дубль бага, подбирает корректные даты в прошлом и ничего не отправляет без подтверждения. Они вызывают модель на твоём аккаунте, поэтому запускаются вручную перед релизом. На Linux для песочницы Bash нужны `bubblewrap` и `socat`.

Песочница также не запускается, если в `~/.docker` есть символические ссылки (в ошибке упоминается хранилище учётных данных Docker). Интеграция Docker Desktop с WSL создаёт две такие ссылки: `contexts` и `features.json`. На время прогона их нужно вынести из `~/.docker`, а потом вернуть; переименовать внутри `~/.docker` недостаточно:

```bash
mkdir -p /tmp/docker-links && mv ~/.docker/contexts ~/.docker/features.json /tmp/docker-links/
claude plugin eval . --scaffold --allow-tools Bash Write Edit --trust-plugin
mv /tmp/docker-links/* ~/.docker/
```

`--case` принимает один glob; указывай его один раз (`--case duplicate-bug`), при повторе флага учитывается только последнее значение.

Релиз:

1. Поднять `version` в `.claude-plugin/plugin.json` (установившие через `/plugin` остаются на старой версии, пока она не изменится).
2. Прогнать evals.
3. `git tag vX.Y.Z && git push origin master --tags`, затем создать GitHub Release из тега с описанием изменений.

## Ограничения

- Связь "blocks / is blocked by" есть только в GitLab Premium, поэтому используется `relates_to`.
- Номер задачи (`iid`) всегда следующий по порядку на момент отправки, даже если дата создания стоит в прошлом.
